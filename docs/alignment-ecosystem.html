unfoldingWord Alignment Stack

Four generations of word-alignment software, read side by side: translationCore 3, gateway-edit, translationCore 4, and this repository. What each one stores, what each one does when a translator edits an aligned verse, and what bible-editor should take from them.

01The short answer

Every unfoldingWord aligner ever shipped identifies a word by the triple (text, occurrence, occurrences). That single choice determines everything else, because occurrences is a verse-global count: typing one extra the rewrites the identity of every other the in the verse. All four systems are, at bottom, four different answers to the damage that causes.

SystemAnswer to “the verse text changed”Consequence for the translator
translationCore 3 Detect and reset. The library refuses to merge and throws InvalidatedAlignments; the tool attempts a position remap but still flags the verse invalid and clears “complete”. Broken-chain icon; verse must be revisited. At export, unresolvable verses are blank-reset one at a time, with consent.
gateway-edit Diff, renumber, and flatten on failure. A sequential word diff renumbers occurrences; if anything throws, the verse USFM is replaced wholesale with plain text. Alignment silently disappears. The caller receives no signal that it happened.
translationCore 4 Reflow what survives, invalidate the rest. Links whose word+occurrence survives are kept and renumbered; anything else leaves the record untouched and marked stale. Honest: the record is preserved but marked not-valid. No link is ever invented.
bible-editor Repair in place, five tiers, fail closed. Alignment lives inside the verse tree and is rewritten locally; if no tier can prove the result, the save is refused. Alignment usually survives an edit untouched. When it cannot, the save is blocked rather than silently lossy.
Headline

bible-editor’s edit engine is the strongest of the four on the axis that matters most — preserving alignment through an ordinary text edit — and it is the only one of the four with a save guard that refuses a lossy write on both client and server. Where it is behind is suggestions (gateway-edit and tc4 run a trained statistical model; we run precomputed frequency tables) and translator-asserted completeness (tc4 has an explicit “done” flag; we infer completeness from an empty word bank, which tc4 abandoned for cause).

02The shared substrate

All four systems read and write the same wire format and share the same word-identity model. The differences are entirely in what they do between reading and writing.

USFM 3 milestones

Alignment on disk at Door43 is USFM 3 milestone markup: a \zaln-s milestone carries the original-language word’s attributes (x-strong, x-lemma, x-morph, x-occurrence, x-occurrences, x-content), wraps one or more target-language \w words, and closes with \zaln-e\*. Milestones nest, so a phrase aligned to a phrase is a chain of nested \zaln-s markers. Non-contiguous alignment is expressed as repeated milestone pairs over the same source words.

Every system parses this with usfm-js. Three of the four then convert it into something else in memory; only bible-editor keeps working on the milestone tree itself.

The identity triple, and why it is the root cause

A word is identified by its surface text, which instance of that text it is in the verse (occurrence, 1-based), and how many instances exist (occurrences). No system stores a stable token id. 

// word-aligner: occurrence is clamped at tokenization time
if (occurrence > occurrences) occurrence = occurrences;
word-aligner/src/js/utils/verseObjects.js:205

Because occurrences is a verse-global count, inserting or deleting any duplicate of a word rewrites the identity triple of every other instance of that word — including instances the translator never touched. That is the structural reason edit-invalidation is so aggressive across the whole family, and why every system needs some form of fuzzy re-matching.

Design observation

tC3’s on-disk format stores only the triple — no positions — which forces a position-recovery pass on every load, acknowledged in the tool’s own comment: “The pain point here is due to the current alignment file format we cannot reliably assume token order. Therefore we must include a frame of reference.” wordAlignment/src/state/actions/index.js:75-77 tc4 has the same gap by choice; its own contract document lists “tC4 stores no token position” as a known divergence from the RCL’s requirements. bible-editor sidesteps it: because the milestones stay in the verse tree, position is the structure.

Version trap

word-aligner-lib and word-aligner-rcl both export a module named AlignmentHelpers with a function named updateAlignmentsToTargetVerse, and they are not the same algorithm. The -lib copy (632 lines) is the older generation: it has no findWordChanges, no adjustTargetOccurrences, no ordered change list, and no repeated-word fixup — just two heuristics that append added words to the word bank and splice out target words whose occurrence no longer resolves. The -rcl copy (1,237 lines) is the current one. Anything resolving AlignmentHelpers from -lib silently gets materially worse occurrence renumbering on repeated words.

05What happens when text is edited

This is the axis on which these four systems genuinely differ, and the one that decides whether a translator loses work. Four philosophies, in the order they were built.

tC3 — detect, repair, but still declare invalid

tC3 splits the job between two components that do not talk to each other. The word-aligner library never repairs: merge() validates stored alignments against the verse string and throws at three separate sites when they disagree — a word in the verse that the alignment data doesn’t know, a word in the word bank that the verse no longer has, and an aligned target word missing from the verse. 

if (verseObjectsNotInAlignmentData.length > 0) {
  if (hasAlignments(alignments)) {
    throw {
      message: `The words "${verseWordsJoined}" from the target language verse are not in the alignment data.`,
      type: 'InvalidatedAlignments',
    };
  } else {
    return useVerseText ? unalignedOrdered : null;
  }
}
word-aligner/src/js/aligner.js:159-169 — all three throws are gated on the verse having alignments at all

The aligner tool answers the same problem independently, in Redux, and it does repair. REPAIR_VERSE_ALIGNMENTS builds an old-position → new-position map using a three-step matcher: exact match, then same-occurrence match, then a fuzzy fallback that accepts a looksLike match if the position is unassigned and adjacent to the previously assigned one. That is what lets a spelling correction keep its alignment. But removing a source word destroys its alignment outright — “TRICKY: removing a source token automatically breaks the alignment” — and, critically, a successful repair still does this: 

let isVerseInvalidated = (wasChanged || isAligned || isAlignmentComplete);
if (isVerseInvalidated) { this.setVerseInvalid(chapter, verse, true, silent); }
this.setVerseFinished(chapter, verse, false);
// TRICKY: if there were no alignments we fix silently
wordAlignment/src/Api.js:424-441

So any verse that was aligned or complete gets the broken-chain icon and loses its completion the moment its text changes, whether or not the repair preserved everything. Only a verse with no alignments at all is fixed silently. At export time, the host’s only remedy for a verse the library still refuses is a blank reset, one verse per pass, behind a confirmation dialog.

gateway-edit — diff and renumber, then flatten

word-aligner-rcl replaced tC3’s repair with a real sequential diff. updateAlignmentsToTargetVerse serializes the verse to USFM, unmerges it into cards, tokenizes the new text, runs findWordChanges (a two-pointer diff producing ordered added/deleted lists with a repeated-word anchor fixup), renumbers every target occurrence against the new text, and re-merges. That part is a genuine advance over tC3.

Then there is the fallback:

try {
  adjustTargetOccurrences(wordChanges, verseAlignments)
  targetVerseUsfm = addAlignmentsToVerseUSFM(newTargetTokens, verseAlignments, newTargetVerse);
  if (targetVerseUsfm === null) {
    console.warn(`updateAlignmentsToTargetVerse() - alignment FAILED for ${newTargetVerse}, removing all alignments`);
    targetVerseUsfm = newTargetVerse;
  }
} catch (e) {
  console.error(`updateAlignmentsToTargetVerse - error thrown finding changes, removing alignments`, e)
  targetVerseUsfm = newTargetVerse
}
word-aligner-rcl/src/helpers/alignmentHelpers.js:930-940 (v1.3.7) — verified still present, same line numbers as v1.3.6
The failure mode this project exists to avoid

newTargetVerse is the caller’s raw plain text: no \zaln, no \w. Both branches replace the entire verse with it — every milestone in the verse is destroyed, including alignment on words the edit never touched. There is a console.warn, and the return value gives the caller no way to tell this happened: it returns the same {targetVerseObjects, targetVerseText} shape either way. A third, quieter degradation sits inside the differ itself, whose own try/catch returns an empty change set on any throw, so occurrences are never renumbered. alignmentHelpers.js:905-908

No test in the RCL exercises the flatten path. Our web/src/lib/alignmentReassembly.ts ported the algorithm’s shape and deliberately refused this branch; that judgment is confirmed against the current release.

tc4 — reflow what survives, invalidate the rest

tc4 calls it reflow, and it is deliberately modest. A link is kept only if its word + occurrence key survives in the new text; survivors get their occurrence counts recomputed; everything else is rebuilt into the word bank. The source side is never touched and no link is ever created. When it cannot help — the record is absent, already invalid, has no placed word, is not stale, or the new text has no words — it returns null and the caller changes nothing:

tc4 · src/data/align/edit.ts:266-268

“In every null case the caller leaves the record exactly as it is: invalidate-and-retain (D36) stays the outcome the I-3 hash already produces.”

The I-3 hash is an md5 of the target verse text stored on the alignment record. When it no longer matches the draft, the verse reads as stale — and staleness, along with an explicit invalid flag, outranks the translator’s done mark. Verse-span changes write an empty record with invalid: true rather than re-keying, under a ruling that reads: “alignments and decisions on the affected verses are invalidate-retain, never re-keyed. The translator re-aligns and re-checks the span.”

This is weaker than what we do — a translator who edits a word loses that alignment where our engine would have kept it — but it is honest. Nothing is invented, nothing is silently dropped, and the record survives to be repaired by hand.

bible-editor — five tiers, degrade locally, fail closed

Because alignment stays inside the verse tree, an edit is a tree rewrite rather than a reconstruction. smartEditVerse runs a ladder and takes the first tier that can prove its result:

  1. No-op — normalized plain text is unchanged.
  2. Marker split — inline markers (\p, \q1, \ts*) are stripped from both sides so they cannot move the diff anchors, then re-placed afterwards.
  3. Relayout — the word sequence is 1:1 unchanged, so only punctuation moves; every \w and \zaln stays put.
  4. Reassembly — the primary engine: unmerge to pivot words carrying their full milestone ancestry, LCS word-diff, re-merge survivors in their exact original milestone chain. Gated so it only fires on genuinely multi-region edits, with a self-check that the rebuilt raw text equals the requested text and that every structural node survives unaltered.
  5. Localized rewrite — the last resort: nodes outside the change range pass through verbatim; an overlapped milestone is split into before/after halves so surviving children keep their source alignment.

Inside the replacement tier there is a further preserve path: when the change spans full words with matching word counts and an element-wise identical punctuation skeleton, each affected \w leaf is rewritten in place and only that word is lifted out of its \zaln ancestors — the translator’s edit invalidates that word’s alignment, and unchanged neighbours stay aligned.

The structural difference

There is no whole-verse fallback. When no tier can prove its output, the result is refused and the save is blocked. The other three systems all have a terminal state in which the verse’s alignment is discarded; this one’s terminal state is “don’t write”.

The measurement that matters

tc4 publishes a training bench: NT, 7,958 aligned verses, 273 s to train, 101 ms per prediction; OT (Genesis + Psalms), 3,994 verses, 137 s / 56 ms. gateway-edit targets an 8-minute train and adapts its complexity budget up or down to hit it, with a 10-minute worker timeout and a low-memory warning reading “Running in Browser — Alignment Training may be slow or crash.”

This contradicts one of our stated reasons

api/src/align.ts:5-8 says “The engine (‘wordMAP’) never runs in the Worker” — correct, and unavoidable in a 128 MB Cloudflare Worker with no filesystem. But docs/alignment-suggestions.md generalizes that into the anti-goal “don’t move inference to the client.” tc4 and gateway-edit both run the full engine in a browser Web Worker, with published timings. The constraint we reasoned from is a server constraint; the client one was never measured here.

That does not mean wordMAP would beat our numbers. Ours are the only measured accuracy figures anywhere in this family — 61.7 precision@1 after the morph phase, against a 57.5 frequency-only baseline — and neither wordMAP implementation publishes any. It means the question is open, and the corpus difference cuts our way: theirs cold-start at zero, ours works from verse one because it is trained on the gold canonical alignments.

Acceptance discipline worth copying

tc4’s bridge layer is stricter than ours in three specific ways, each of which is a small, self-contained rule:

  • A prediction whose source words span two cards is dropped entirely rather than truncated — a partial suggestion is worse than none.
  • rebindSuggestions re-finds a live proposal’s card by the predicted original word, so a merge or split mid-session cannot misplace it.
  • “Mark valid” is refused while any suggestion still stands — you cannot certify a verse you haven’t answered.

The RCL has the same instinct expressed differently: a card is wholly suggested or wholly manual, with the comment “We can’t add in suggested additional targets because we can’t represent a mixture of suggested and manual.” Touching a suggested card promotes it to manual immediately.

07Completeness and validation

Every system needs to answer “is this verse finished?” Three of the four learned that an empty word bank is the wrong answer. We are the one that hasn’t.

tc4 decision D73, verbatim context

“The Align tool derived ‘valid’ from ‘the word bank is empty’” — which fails a translator who legitimately leaves words unaligned. The replacement rules: all-aligned implies done; “Mark valid” behaves like other checks; any edit takes it back; the field is additive so the schema version doesn’t move; and the \zaln export ignores it entirely. tC3 had already reached the same design a decade earlier with its “Alignment Complete” toggle.

Our verseHasUnalignedWork is precisely the heuristic both of them abandoned. It is why the chain icon reads red on verses a translator considers finished — and it is the same class of problem as JER 36:11, where a deliberate human alignment choice reads to the system as damage.

Defect detection beyond completeness

bible-editor is alone in shipping data-defect detectors that are separate from completeness: reused source tokens (one Hebrew word claimed by two distinct position sequences), doubled source milestones, glued milestones spanning a maqqef, occurrence counts out of range. These surface as red chips in the panel and as server-side lint checks. tC3’s nearest equivalent is a console.error in its render validator; gateway-edit has none.

08Data-loss guards

The question here is narrow: can a write leave the store with less alignment than it had, without anyone being told?

  • tC3 — no guard at write time. The tool rewrites every chapter of the book on every state change (“TRICKY: we validate the entire book so we must write all chapters”). Protection is post-hoc: validation on load, and the export-time reset dialog.
  • gateway-edit — none. The completeness icon is display-only, Save is never disabled, and the only confirmation is “do you want to accept the suggested alignments.” The flatten path writes through.
  • tc4 — the I-3 hash marks a record stale but never blocks a write. Writes go through a compare-and-swap on the file’s md5, which protects against concurrent loss, not semantic loss.
  • bible-editor — an LCS-based delta analysis runs on both client and server. It links before/after words and reports lost (a previously aligned word is now bare) or changed_source; guardBlocksSave refuses the write unless the intent is alignment_edit or confirmed_text_edit. The aligner panel additionally prompts before an intentional unalign, and the nightly export carries a severity-classified shrink backstop.
A hard-won rule worth restating

Our guard carries an explicit warning against re-adding a wordSequenceUnchanged narrowing, naming the commit and the 1CH 4:21 / NUM 24 incident. The lesson generalizes to anything in this document: use a signal like that for the wording of an alert, never to narrow the refusal decision. That exemption is what let collateral alignment loss ship.

Our own blind spot, for symmetry

The guard covers alignment, not markers. Issue #606: a DOM capture that lost its marker chips deleted every \q in three HOS verses while every word round-tripped perfectly — so preservedAlignment stayed true, the guard didn’t fire, the unaligned-word toast didn’t fire, and the nightly export carried the loss to Door43 for a fortnight. None of the other three systems would have caught it either, but it is the shape of failure our guard is blind to.

09Interaction models

Three of the four aligners are bespoke. That is a stronger signal than it first appears.

tC3 uses react-dnd 2.5.4 with the HTML5 backend, and pays for it: left-side un-merging is dead code, blocked on a react-dnd bug, and multi-word drag previews are static PNG images (multi_drag_preview_2 … _15) because “react-dnd’s custom drag layer has very poor performance.” Everything since has used native HTML5 drag-and-drop.

More interesting: tc4 declares @gabrielaillet/word-aligner-rcl as a devDependency and never imports it. Its own evidence document is blunt — “git log -S'word-aligner-rcl' -- src prints nothing: no source file ever imported it” — and its architecture note states that “the check and alignment surfaces are design-native.” The fork is retained purely as a written contract. Two independent teams, working on the same problem at the same time, both concluded the shared aligner component was not worth embedding. Our own decision to build a custom aligner rather than use enhanced-word-aligner-rcl sits in good company.

10Test posture

The spread here is wider than anywhere else in the comparison, and it correlates with how much damage each system’s failure mode does.

  • gateway-edit has zero alignment tests. Its jest config excludes components, so the two aligner components are untestable by design, and collectCoverageFrom uses a single-star glob that doesn’t recurse. The RCL beneath it has a good data-driven suite — 23 edit scenarios, several multi-step, asserting exact USFM round-trip, word conservation, and non-mutation of the input — but no test exercises the flatten fallback.
  • tC3’s tool has the largest reducer suite in the family: ~2.3k lines on alignment reducers including a dedicated “repair alignments” block whose cases are the real invariants (“edits target token from the midst of identical tokens”, “removes duplicate tokens”), ~2.3k more on suggestions, and an API suite that pins the exact invalidation matrix. Its word-aligner core, however, has no test for any of the three InvalidatedAlignments throws — the entire contract callers depend on is unexercised.
  • tc4 has nine focused suites plus something the others lack: a conformance harness that runs the real libraries over a real corpus, proving round-trip on every sidecar verse and that full-book aligned USFM can be produced from stored data alone.
  • bible-editor has ~7.4k lines across alignment.test.mjs (≈60 named cases), replace.test.mjs (78+ cases), and the delta-guard suites, under a standing rule that every edit-path bug gets a regression case. The cases are named after real verses — 1CH 4:21, NUM 24:19, JER 29:31, ZEC 6:13 — which is the same discipline tc4 applies via fixtures.
The one test idea we don’t have

tc4’s conformance harness runs against a real corpus rather than synthetic fixtures. Our STATE.md already records a case where that distinction bites: the \d Psalm-superscription wrapper shape modelled throughout alignment.ts “does not match either real shape,” so those code paths may be exercised only by their own fixtures. A corpus gate over actual DCS-fetched content is the kind of test that finds that class of bug.

11What to adopt

Ranked by value per unit of risk. Each is independently shippable.

  1. 1

    An explicit “alignment done” flag

    Add a translator-asserted completion mark, stored additively (absent means not done, never false), outranked by any subsequent edit, and ignored by the export renderer. Drive the chain icon from done rather than from an empty word bank; keep verseHasUnalignedWork as the auto-set trigger, not as the verdict.

    Precedent: tC3’s “Alignment Complete” toggle and tc4’s D73, which names our exact heuristic as the thing it replaced. Why now: it is the clean answer to a translator who deliberately leaves a word unaligned, and it aligns the indicator with the standing ruling that an unaligned word or two is no reason to hold back a sync.

  2. 2

    A conformance gate over real content

    A harness that round-trips every verse of a real DCS-fetched book through parseAlignment → serializeAlignment and asserts byte-equality, plus a full-book export rendered from stored data alone. Run it in CI over a fixed corpus that includes Psalms with superscriptions and the Hebrew books that exercise normalization.

    Precedent: tc4’s conformance/validate.mjs. Why now: the unresolved \d wrapper question in STATE.md is exactly what this catches, and we already have the importer to build the corpus.

  3. 3

    Suggestion-acceptance discipline

    Three rules from tc4’s bridge: drop a cross-card prediction entirely rather than truncating it; re-bind live ghosts to their card by the predicted source word so a merge or split can’t misplace them; and refuse to mark a verse done while an unanswered suggestion stands.

    Precedent: tc4 suggest.ts; the RCL reaches the same conclusion from the other direction (a card is wholly suggested or wholly manual). Why now: our computeGhosts claims words greedily across two passes, and nothing was found that re-binds a ghost through a mid-session card merge. Pairs naturally with #1.

  4. 4

    Settle the in-browser wordMAP question with a measurement

    Run uw-wordmapbooster in a Web Worker against a held-out book and score it with the existing scripts/eval-aligner.mjs harness. Compare precision@1 and false-positive rate against the shipped 61.7 / 6.1. If it wins, the interesting shape is a hybrid: our D1 prior for cold start, a locally trained booster as the translator aligns.

    Precedent: tc4 (273 s train, 101 ms predict) and gateway-edit (8-minute target, adaptive complexity) both prove it runs in a browser. Why now: our written anti-goal generalized a Cloudflare Worker constraint into a client one that was never measured — and we are the only party in this family with an accuracy harness to settle it.

  5. 5

    A tokenizer-agreement test

    We keep WORD_CHAR/WORD_RUN_RE byte-identical between replace.ts and alignmentReassembly.ts by comment and discipline. Make it an assertion: one fixture corpus, token-for-token and occurrence-for-occurrence agreement between every tokenizer in the codebase.

    Precedent: tc4 named this as an unmeasured risk in its platform notes and closed it with test/align-tokenize.test.ts. Why now: cheap, and the failure it prevents is silent misalignment rather than a crash.

  6. 6

    Keyboard shortcuts in the aligner

    tC3 ships seven: refresh suggestions, accept, reject, clear, toggle complete, and navigation. Our aligner is mouse-only, with no touch or pointer fallback either.

    Precedent: wordAlignment/src/components/Container.js via react-hotkeys. Why now: aligning a book is thousands of repetitions; it is the one place in the app where shortcuts pay for themselves outright.

12What not to adopt

  • Sidecar storage. Both translationCore generations store alignment outside the text. tc4’s reason is specific and does not apply to us: its host’s drafting editor destroys milestone markup on save, so “no \zaln at rest” is a defensive invariant against a platform it doesn’t control. We own our editor. Keeping milestones in the verse tree is what makes position structural rather than reconstructed, and it is the reason our edit engine can degrade locally at all.
  • The whole-verse flatten fallback. Already refused in alignmentReassembly.ts, and the refusal is now verified against the current release rather than a remembered line number. Nothing here changes that judgment.
  • Invalidate-and-retain as the primary edit response. tc4’s reflow keeps a link only on exact word + occurrence survival and otherwise hands the verse back to the human. Our ladder is materially stronger. Adopt tc4’s honesty (the done flag, the staleness hash) without adopting its weaker repair.
  • Rejecting non-adjacent merges. tc4 refuses them so that flattened topWords stay in verse order for export. We solve the same constraint better with canonicalizeSource, which re-sorts a merged chain into verse order regardless of drag direction.
  • react-dnd. tC3’s experience is a closed case: a blocked feature and static PNG drag previews. Every system built since uses native HTML5 drag-and-drop.
  • Whole-book rewrites on every state change. tC3 writes every chapter of the book on each Redux change, flagged in its own comments as a performance smell. Our per-verse outbox with If-Match is the right model.

13Limits of this review

  • Nothing was executed. No test suite was run, no app was launched, no benchmark was reproduced. Every claim is from reading source at the commits listed below. Performance and accuracy numbers attributed to other projects are their published figures, not our measurements.
  • node_modules was not installed anywhere. Package-internal behavior was read from each package’s own repository at its current HEAD, which may be ahead of the version the consuming app pins. This matters most for tC3: its aligner tool pins word-aligner@0.2.12, and the library repository read here is 1.1.1.
  • Two gateway-edit conversion claims are unverified. That its alignment lives inline in \zaln and that scripture saves follow the same user-branch → PR flow as its resource cards are both consistent with what the app does, but the writers live in single-scripture-rcl, which was not read.
  • tc4’s export path may be unwired. mergeVerseToZalnUsfm has no caller in src/ at the commit read; it is proven only by the conformance harness.
  • No accuracy figures exist for any wordMAP implementation in this family. Any claim that an in-browser engine would beat our 61.7 precision@1 is speculation until recommendation #4 is run.
  • Project canon was not consulted. The oddkit MCP server this project uses as its epistemic guide is not configured in the session that produced this document, and graft failed to connect. Nothing here was checked against recorded decisions or constraints beyond what is in this repository’s own files.
