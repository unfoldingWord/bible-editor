# bp-assistant ↔ bible-editor: chapter-intro hint contract

## Status

**Proposed.** bible-editor's side is implemented (issue #819): the notes
pipeline gathers unresolved chapter-intro hint comments and sends them as
`options.introHints`. This needs a matching change on the bp-assistant side
(`tn-writer`/the intro-generation skill) to actually weave the hints into its
intro prompt — the wire is live and harmless to ignore in the meantime
(`introHints` simply won't affect output until consumed).

This is a sibling to, not a replacement for,
[`docs/bp-assistant-tn-hints-contract.md`](./bp-assistant-tn-hints-contract.md).
That contract is per-verse and id-keyed (bp-assistant echoes a `rowId` back
into the TSV `ID` column so bible-editor can match the expansion to its
stub). A chapter intro isn't generated by expanding one row in place — it's
freeform prose for the whole chapter — so there's no id to round-trip.
`introHints` is a plain, one-way, chapter-scoped prompt-context bundle
instead.

## Why this exists

The only lever an editor previously had over an AI-generated chapter intro
was `preserve` on the old intro row, which protects it from deletion but
feeds the AI nothing. There was no way to say "make sure the intro mentions
X" the way a verse hint lets an editor steer a single TN note. See #819 for
the full background.

## What bible-editor sends

`POST /api/pipeline/start` body's existing optional `options` object gains
`introHints`, sent only for `pipelineType: "notes"` runs and only when at
least one hint exists in the requested chapter range:

```json
{
  "pipelineType": "notes",
  "book": "ZEC",
  "startChapter": 3,
  "endChapter": 4,
  "username": "...",
  "sessionKey": "...",
  "options": {
    "introHints": [
      { "chapter": 3, "note": "Mention the covenant themes in vv 1-6." },
      { "chapter": 3, "note": "There's scholarly disagreement about the date; note it." },
      { "chapter": 4, "note": "The outline should call out the shift in audience." }
    ]
  }
}
```

Field semantics:

- `chapter` — integer. Which chapter's intro the hint applies to. A
  multi-chapter run (`startChapter` .. `endChapter`) can carry hints for
  several chapters in one array; group by `chapter` before use.
- `note` — string, 1-5000 chars (matches the internal-comment body limit).
  Free-form editor guidance — no schema beyond that. May be anything from a
  one-line reminder to several sentences.

`introHints` may be empty or absent on any run (omitted, not an empty array,
when there is nothing to send). When absent, behave exactly as today.

## What `tn-writer` (or whichever skill generates the intro) should do

For each chapter in the run that has one or more `introHints` entries: fold
all of that chapter's notes into the intro-generation prompt as guidance —
e.g. "the translator has asked that the intro also address: <note 1>; <note
2>; ...". They are hints to incorporate, not verbatim text to insert — write
a normal, well-formed intro that reflects the guidance, the same way a
`seed` under the verse-hint contract is expanded rather than echoed.

Chapters in the run with no `introHints` entries: behave exactly as today.

There is nothing to echo back. Unlike a verse hint, no TSV column or output
field needs to carry anything correlating back to bible-editor — the hints
are consumed purely as prompt input.

## What bible-editor does on its side

For your awareness (already implemented):

- **Storage**: an editor leaves a hint via the *existing* internal-comments
  UI (`CommentsPopover`), anchored to the chapter's verse-0 "intro" row with
  no `rowKind`/`rowId` (a verse-level comment, `kind: "note"`) — the same
  affordance already used for "add a comment on this verse," not a new UI
  surface.
- **Outbound** (`api/src/pipelines.ts`): at `/api/pipelines/start` time, for
  `pipelineType: "notes"`, the proxy selects all unresolved, non-reply,
  verse-0, row-less, `kind = "note"` comments in the requested chapter range
  and folds them into `options.introHints` (see `api/src/introHints.ts`).
- **Consumption**: sent hints are marked resolved immediately at the same
  D1-read-at-start-time point the verse hints are captured (see
  `resolveIntroHintComments`, `api/src/comments.ts`) — not gated on the job
  finishing, since there's no id to correlate a future apply against. An
  editor who wants to add more guidance just leaves a new comment (or
  reopens a resolved one from the comments panel); either way it's picked
  up by the next run.

## Verification

bp-assistant smoke test (once the intro skill consumes `introHints`):

1. Call the intro-generation skill with `options.introHints` containing two
   entries for the same chapter and one for a different chapter in the run.
2. Confirm the first chapter's intro visibly reflects both notes; the second
   chapter's intro reflects its own note only; a chapter with no hints
   generates its normal, unguided intro.

bible-editor smoke test (already testable against `main`):

1. Add one or more internal comments (kind: note) on a chapter's intro
   (verse 0), leaving them unresolved.
2. Trigger the notes pipeline for that chapter.
3. Confirm: `pipeline_jobs.options_json` for the created job contains
   `introHints` with the expected `(chapter, note)` pairs; the source
   comments are now resolved (and attributed to the user who triggered the
   run) in the comments panel; triggering the pipeline again for the same
   chapter sends no `introHints` (nothing left unresolved) unless a new
   comment was added.
